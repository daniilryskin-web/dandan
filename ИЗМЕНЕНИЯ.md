# Что изменено и как проверить

Этот документ описывает правки, сделанные по жалобам: «Ozon не работает», «WB
очень медленный», «данные сохраняются криво», «интерфейс надо улучшить».

## Сначала — честно про «100% без ошибок»

Парсер маркетплейсов в принципе **не может** работать со 100% гарантией, и важно
понимать почему — чтобы не было ложных ожиданий:

- **WB и Ozon активно меняют вёрстку и защищаются от парсинга** (Cloudflare,
  TLS-fingerprint, лимиты запросов). Любой парсер периодически нужно чинить —
  это нормальная эксплуатация, а не дефект.
- **Реестры (ФСА/SWIS) тоже меняются** и иногда отдают 403/таймауты.
- **Сверка «название карточки ↔ название в реестре» по любым категориям —
  это нечёткое сравнение.** Можно сделать очень хорошо (и сделано), но
  «абсолютные 100% по любым категориям» недостижимы — формулировки в карточке и
  в сертификате почти никогда не совпадают дословно.

Поэтому цель правок — **существенно быстрее, надёжнее и чище**, плюс защита от
регрессий тестами. Где возможны ошибки — программа теперь честно помечает строку
(«проверить вручную», «нет ссылки», «документ недействителен»), а не выдаёт
выдуманный результат.

## v54.5 (2026-06-21): аналитика отчёта + кэш карточек

Четыре доработки (по согласованию). Все офлайн-логики покрыты тестами
`tests/test_v55_features.py` (40 проверок) и входят в `tests/run_all.py`.

- **№5 — лист «Причины».** Раньше сводка была только по статусам. Теперь в отчёте
  есть отдельный лист с разбивкой проблемных вердиктов **по причинам** (конфликт
  категорий / возраст 007 vs 017 / пол / недействующий документ / низкое сходство
  и т.д.) + столбчатый график. Видно, что именно даёт основную массу проблем.
- **№6 — лист «Продавцы».** Агрегаты по каждому продавцу: всего, OK,
  НЕСООТВЕТСТВИЕ, ВРУЧНУЮ, недействующих, **% проблемных** (с подсветкой).
  Сразу видно, у кого системные проблемы с документами.
- **№7 — лист «Изменения».** Дифф с прошлым прогоном: что **впервые** стало
  НЕСООТВЕТСТВИЕ, где проблема устранена, у кого изменился статус документа
  (Действует→Прекращён), что истекло, что появилось/исчезло. Снимок хранится
  рядом с отчётом как `<output>.prev.json` и обновляется только на финальном
  сохранении прогона **с вердиктами** (этап сбора ссылок снимок не затирает).
- **№8 — глобальный кэш карточек (этап 1).** SQLite-кэш `card_cache.sqlite` по
  `nm_id`: уже собранная ссылка на реестр берётся мгновенно, в т.ч. для карточек
  из **других** запросов/прогонов (в отличие от resume, привязанного к одному
  CSV). Кэшируются только успешно собранные ссылки; свежесть — 7 дней.
  Управление: `--card-cache` (по умолч. вкл.), `--card-cache-file`,
  `--card-cache-ttl-days` (0 = бессрочно).

Проверка: `python3 tests/run_all.py` → «ВСЕ ТЕСТЫ ЗЕЛЁНЫЕ». В Excel-отчёте после
прогона появятся листы **«Причины»**, **«Продавцы»**, **«Изменения»**.

## v54.6 (2026-06-21): скорость и живучесть больших прогонов

Три доработки про производительность и надёжность. Логика покрыта тестами
`tests/test_v546_pipeline.py` (27 проверок), входят в `tests/run_all.py`.

- **№1 — Конвейер (этап 2 параллельно этапу 1).** Раньше этап 2 стартовал только
  после ПОЛНОГО завершения сбора ссылок. Теперь, как только собрано ≥300 ссылок,
  параллельно запускается проход этапа 2 — он **прогревает кэш реестров**, пока
  этап 1 ещё дособирает. После — финальный проход этапа 2 добирает остаток (уже
  распарсенное берётся из кэша мгновенно). **Корректность гарантирована:** источник
  истины — финальный проход; параллельный лишь ускоряет (в худшем случае — без
  эффекта, результат не страдает). Параллельный проход не трогает дифф-снимок
  (`--diff-snapshot false`). Выигрыш максимален на тёплых/кэшированных прогонах.
  Отключается настройкой `pipeline_overlap` в GUI.
- **№2 — Живучесть прогона (авто-возобновление после краха).** Движок теперь
  выходит с **ненулевым кодом** при критической ошибке (раньше падал, но код был 0
  — сбой был незаметен). GUI это видит и **автоматически перезапускает** прогон до
  3 раз с паузой; resume (CSV ссылок) и постоянные кэши реестров/карточек
  продолжают **с чекпойнта**. Чистое завершение и остановка пользователем
  перезапуск НЕ вызывают. *Чтобы «прошло 11698/17900 и всё» не повторялось.*
- **№3 — Предстартовая оценка времени.** Перед каждым этапом печатается грубая
  оценка: «этап 1: N карточек → ~X»; «этап 2: ФСА M (медленный режим ~25/мин),
  СВИС/прочие K → ~Y ч». Сразу видно, что прогон многочасовой, без сюрприза «11
  часов». Это прикидка ДО запуска (живой ETA по факту считается отдельно).

Проверка: `python3 tests/run_all.py` → «ВСЕ ТЕСТЫ ЗЕЛЁНЫЕ». В логе перед этапами
появятся строки «⏱ Предварительная оценка…», при крахе — «⚠️ Авто-перезапуск…»,
при конвейере — «⚡ Конвейер: этап 2 пошёл параллельно…».

> Важно про среду разработки: правки делались в изолированном окружении **без
> доступа к живым WB/Ozon/ФСА** (все эти домены там заблокированы). Поэтому
> логика покрыта офлайн-тестами, но **финальную проверку на живых сайтах нужно
> сделать на вашей машине** по чек-листу ниже.

## Что конкретно сделано

### 1. WB больше не тормозит на карточках без документа (главный источник медленности)
- `certificate.json` по basket-шардам раньше опрашивался **последовательно**:
  для карточки без документа это до N таймаутов подряд (десятки секунд на одну
  карточку).
- Теперь все шарды проверяются **параллельно**; как только найдена ссылка на
  реестр — остальные запросы немедленно отменяются. Худший случай (документа
  нет) — это **примерно один таймаут вместо суммы**. На тесте 8 шардов по 0.2с:
  было ~1.6с → стало 0.20с (**в ~8 раз быстрее**).
- Заодно починена шардировка для **новых товаров**: таблица basket больше не
  обрывается на `basket-30`, primary-шард для высоких `nm_id` вычисляется
  корректно (иначе такие карточки зря перебирали все шарды и могли ошибочно
  помечаться «без документа»).
- Контракт статусов сбора ссылок сохранён 1:1, поведение остального кода не
  меняется. Файл: `main_v39.py`. Тест: `tests/test_cert_fetch.py`.

### 2. «Данные сохраняются криво» — защита Excel от падения
- `openpyxl` **роняет весь отчёт** (`IllegalCharacterError`) на управляющих
  символах, которые регулярно попадаются в спарсенном тексте (наименования и
  описания из карточек/реестров). Это и есть «криво/неполные выгрузки».
- Добавлена функция `_xlsx_safe` во все три движка (`main_v39`, `ozon_parser`,
  `main_brand`) и применена ко всем строкам данных: control-символы вычищаются,
  переводы строк/табуляции схлопываются в пробел (колонки больше не
  «разъезжаются»), длина режется под лимит ячейки Excel, **числа остаются
  числами** (для сортировки/формата). Тест: `tests/test_xlsx_safe.py`.

### 3. Ozon — реестры и вердикт теперь на всех путях
- Раньше **финальный вердикт сверки названий считал только Playwright-путь**, а
  HTTP-путь молча отдавал карточки без главного результата программы.
- Теперь HTTP-пайплайн (`run_full_pipeline`) обогащает строки реестрами **и**
  считает вердикт той же функцией, что и WB (`compare_product_names`), поэтому
  результат единообразен на обоих маркетплейсах. Тест: `tests/test_ozon_verdict.py`.
- `curl_cffi`-fallback теперь пробует **две** базы composer-api: `api.ozon.ru`
  и `www.ozon.ru` — вторая часто отвечает там, где первая уже отдаёт 403.

### 4. Прогресс в интерфейсе стал честным
- Окно вытаскивало прогресс слабым регэкспом `\d+/\d+` прямо из логов и ловило
  **ложные срабатывания** — «повтор 2/5», «45/мин», соотношение продавцов —
  из-за чего полоса прогресса скакала.
- Движки (WB-поиск, WB-бренд, Ozon) теперь печатают **однозначный маркер**
  `@@PROGRESS@@ stage=.. done=.. total=..`, который окно парсит в первую
  очередь; запасной разбор огрублён фильтром. На экране «Очередь» появился
  **ярлык этапа** (сбор ссылок / проверка реестров / поиск / карточки).
  Тест: `tests/test_progress.py`.

### 5. Сквозная проверка отчёта (защита от регрессий)
- `tests/test_report_e2e.py` прогоняет **настоящий** путь сохранения
  (`ResultStore._save_xlsx` и `ozon.save_xlsx`) на «грязных» данных: проверяет,
  что отчёт не падает, создаются все листы (results / review / summary /
  Сводка / Подробности), на «Сводке» есть графики, а в ячейках нет «мусора».

### 6. Предполётная диагностика окружения
- Новый инструмент: `python preflight.py` (или `python preflight.py --network`).
  За пару секунд показывает понятным языком, **чего не хватает**: несовместимый
  Python, не установленные пакеты (с пояснением назначения каждого), не
  скачанный браузер Playwright, а с `--network` — доступность WB/Ozon/ФСА/SWIS.
  Помогает самому понять причину, не читая трейсбеки. Тест:
  `tests/test_preflight.py`.

### 7. Больше данных из карточки WB
- В выгрузку добавлены поля **«Цвет»** и **«Корневой ID (WB)»** (группировка
  вариантов одного товара). Извлечение защитное (пусто, если поля нет),
  схема обратносовместима — старые выгрузки не ломаются.

### 8. Интерфейс: полиш и защита от поломок
- Прогресс и **ярлык этапа** теперь приходят со **всех** путей: WB (HTTP и
  браузерный), реестры WB, Ozon (HTTP и основной браузерный Playwright) — раньше
  на части путей полоса в окне стояла.
- Визуальный полиш (только дополняющие CSS-правила, без переделки структуры):
  мягкие тени и hover-подъём карточек/KPI/графиков, градиент и выразительный
  hover главной кнопки, доступный фокус по клавиатуре, акцентная полоса
  активного пункта меню, ровные цифры KPI, более плавная смена экранов.
- `tests/check_frontend.py` — защита окна: проверяет баланс тегов/скобок и
  (при наличии `node`) гоняет `node --check` по JS. Главный риск интерфейса —
  синтаксическая ошибка в JS рушит всё окно; теперь это ловится до запуска.

> Примечание: графики на экранах «Очередь» и «Результаты» уже были (Chart.js
> встроен в `vendor/`). В этой сессии интерфейс не переписывался — только
> аккуратно усилен, чтобы ничего из рабочего не сломать.

## Как установить и запустить (на вашей машине)

> Перед первым запуском удобно прогнать `python preflight.py` — он сразу
> подскажет, всё ли установлено.

```bash
python -m pip install -U -r requirements.txt
python -m playwright install chromium
python wb_checker.py            # приложение с интерфейсом
```

## Чек-лист проверки

1. **Офлайн-тесты (быстро, без интернета):**
   ```bash
   python tests/run_all.py
   ```
   Ожидается «ВСЕ ТЕСТЫ ЗЕЛЁНЫЕ ✅».

2. **WB — скорость и данные.** Запустите небольшой поиск (например, лимит 50).
   Проверьте, что:
   - этап сбора ссылок идёт заметно быстрее, чем раньше, особенно когда много
     карточек без документов;
   - открывается `*.xlsx`, листы `results` / `Подробности` / `Сводка` на месте,
     колонки не съехали, в ячейках нет «мусора».

3. **Ozon.** Запустите поиск. Если основной (Playwright) путь упрётся в
   Cloudflare — проверьте HTTP-путь: добавьте `--use-playwright false` (нужен
   установленный `curl_cffi`). В выгрузке у строк с найденной ссылкой на реестр
   должен появиться вердикт (`OK` / `НЕСООТВЕТСТВИЕ` / `ПРОВЕРИТЬ ВРУЧНУЮ`).

4. Если что-то не парсится — пришлите лог прогона (вкладка «Логи» / кнопка
   «Диагностика»): по нему видно, это блокировка сайта, отсутствие зависимости
   или изменение вёрстки.

## Что можно докрутить дальше (по приоритету)
- **Интерфейс**: живые прогресс-бары по этапам и счётчик ETA; крупные сводные
  графики на экране «Результаты» (Chart.js уже встроен в `vendor/`).
- **WB**: после параллельного перебора можно безопасно увеличить охват шардов
  (`--cert-max-hosts`) — теперь это почти не стоит времени, но повышает точность
  «есть/нет документа».
- **Ozon**: основной путь — браузерный (Playwright), он чувствителен к
  Cloudflare; стоит проверить, какой путь стабильнее именно на ваших запросах,
  и сделать его основным.
