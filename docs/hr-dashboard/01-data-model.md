# 01. Модель данных

## 1.1. Что не так с исходной таблицей (и почему это важно)

Исходная структура:

```
№ | Ответственный за направление | Непосредственный руководитель | Проект / функция |
Продукт (кратко) | Роль | ФИО (штат) | Текущая ЗП, gross
```

Три проблемы, каждая из которых искажает цифры:

**Проблема 1. Зернистость.** Строка — это *назначение* (человек × проект × продукт × роль), а не человек. Сотрудник в трёх проектах = три строки с одинаковой зарплатой. Любой `SUM(ЗП)` завышает ФОТ. Любой `AVG(ЗП)` смещён в сторону тех, кто занят в большем числе проектов.

**Проблема 2. Смешение сущностей.** Зарплата — атрибут *сотрудника*. Роль — атрибут *назначения* (в одном проекте человек тимлид, в другом просто разработчик). Ответственный — атрибут *проекта*. Всё это лежит в одной плоской таблице, из-за чего атрибуты дублируются и рассинхронизируются: поменяли ЗП в одной строке, забыли в двух других — и дашборд врёт.

**Проблема 3. Нет измерения объёма.** Непонятно, человек в проекте на 5% времени или на 100%. Без этого нельзя ни посчитать стоимость проекта, ни увидеть перегруз.

## 1.2. Целевая модель: 2 обязательные таблицы + 2 справочника

```
                 ┌─────────────────────────────┐
                 │  dim_Сотрудники (справочник)│
                 │  ─────────────────────────  │
                 │  ID сотрудника  (ключ)      │
                 │  ФИО                        │
                 │  Текущая ЗП, gross          │
                 │  Грейд                      │
                 │  Тип занятости              │
                 │  Дата найма                 │
                 │  Дата последнего пересмотра │
                 │  Город / юр. лицо           │
                 └──────────────┬──────────────┘
                                │ 1
                                │
                                │ N
   ┌────────────────────────────┴────────────────────────────┐
   │  fact_Назначения  (ваша исходная таблица + 1 столбец)   │
   │  ─────────────────────────────────────────────────────  │
   │  №  (ключ назначения)                                   │
   │  ID сотрудника        → dim_Сотрудники                  │
   │  Проект / функция     → dim_Проекты                     │
   │  Продукт (кратко)                                       │
   │  Роль                                                   │
   │  Доля занятости, %    ← ГЛАВНОЕ ДОБАВЛЕНИЕ              │
   │  Непосредственный руководитель                          │
   └──────────────┬──────────────────────────────────────────┘
                  │ N
                  │ 1
   ┌──────────────┴──────────────┐   ┌──────────────────────────┐
   │  dim_Проекты (справочник)   │   │ dim_Рынок (справочник)   │
   │  ─────────────────────────  │   │ ──────────────────────── │
   │  Проект / функция  (ключ)   │   │ Роль        (ключ)       │
   │  Ответственный              │   │ Грейд       (ключ)       │
   │  Тип направления            │   │ Рынок P25 / P50 / P75    │
   │  Статус                     │   │ Источник, дата обзора    │
   └─────────────────────────────┘   └──────────────────────────┘
```

**Почему это лучше плоской таблицы:**
- зарплата хранится ровно в одном месте → не рассинхронизируется;
- «Ответственный» хранится один раз на проект → нельзя случайно поставить двух разных ответственных на один проект;
- рыночные вилки подключаются/обновляются отдельно, не трогая основные данные;
- в DataLens всё это соединяется в один датасет через «Связи» (JOIN) и с точки зрения построения чартов остаётся одной плоской таблицей.

### Про ключ сотрудника

**Не соединяйте по ФИО.** «Иванов И.И.», «Иванов Иван Иванович» и «Иванов  И.И.» (двойной пробел) — три разных человека для BI. Заведите столбец `ID сотрудника` (можно просто порядковый номер в справочнике) и подтягивайте ФИО в fact-таблицу через `VLOOKUP` — это заодно устранит опечатки в написании.

Если менять структуру совсем не хочется — оставьте ФИО ключом, но обязательно прогоните нормализацию:
```
=TRIM(PROPER(A2))
```
и один раз сверьте список уникальных ФИО (`=UNIQUE(...)`) глазами — там почти наверняка найдутся 2–3 дубля с разным написанием.

## 1.3. Минимальный вариант «не хочу три таблицы»

Если разносить на 4 таблицы не хочется, работайте с одной плоской, но добавьте в неё эти столбцы:

| Столбец | Тип | Обязательность | Зачем |
|---|---|---|---|
| `Доля занятости` | число 0–1 | **обязательно** | Без него ФОТ и загрузка считаются неверно |
| `Грейд` | текст | **обязательно** | Без него сравнение ЗП даёт ложные выбросы |
| `Первичное назначение` | 0/1 | **обязательно** (формула ниже) | Пуленепробиваемый подсчёт уникальных людей и ФОТ |
| `ID сотрудника` | число | сильно желательно | Защита от опечаток в ФИО |
| `Функция` | текст | желательно | Группировка 30 ролей в 5–6 функций |
| `Тип занятости` | текст | желательно | Штат / аутстафф / ГПХ считаются по-разному |
| `Дата найма` | дата | желательно | Даёт стаж и связку «стаж ↔ ЗП» |
| `Дата среза` | дата | на будущее | Открывает всю динамику. Заполнить одинаковым значением сейчас |
| `Стадия продукта` | текст | для контура 2 | idea / MVP / growth / mature / support |

Готовый шаблон — `templates/assignments_template.csv`.

## 1.4. Формулы подготовки данных в Google Sheets

Считать это **в источнике, а не в DataLens** — так надёжнее: формулы прозрачны, результат видно глазами, и не зависит от особенностей LOD-выражений.

Допущения по колонкам (подставьте свои буквы):
`B` — Ответственный, `C` — Руководитель, `D` — Проект, `E` — Продукт, `F` — Роль, `G` — ФИО, `H` — ЗП, `I` — Доля занятости, `J` — Грейд.

### Авто-деление занятости 1/N (если проставить доли вручную нельзя)

```
=IFERROR(ROUND(1 / COUNTIF($G$2:$G, $G2), 3), 0)
```

Человек в трёх строках получает по 0.333. Грубо, но сумма долей по каждому человеку = 1, и ФОТ сходится точно. Позже доли можно уточнить вручную там, где это важно.

### Флаг первичного назначения

```
=IF(COUNTIF($G$2:$G2, $G2) = 1, 1, 0)
```

Обратите внимание на «якорь наполовину» — `$G$2:$G2`. Формула ставит 1 только первой встретившейся строке сотрудника. Дальше `SUM(Первичное)` = число уникальных людей, а `SUMIF(Первичное; 1; ЗП)` = настоящий ФОТ, без всяких LOD.

Хотите, чтобы «первичным» считалось назначение с максимальной долей (это правильнее — так основной проект человека определяется по факту, а не по порядку строк):

```
=IF($I2 = MAXIFS($I:$I, $G:$G, $G2), IF(COUNTIFS($G$2:$G2, $G2, $I$2:$I2, $I2) = 1, 1, 0), 0)
```

### Число назначений и проектов у сотрудника

```
Назначений:  =COUNTIF($G:$G, $G2)
Проектов:    =SUMPRODUCT((($G$2:$G$999=$G2)*($D$2:$D$999<>""))/COUNTIFS($G$2:$G$999,$G2&"",$D$2:$D$999,$D$2:$D$999&""))
```

Вторая формула — классический подсчёт уникальных значений по условию. Если она пугает, есть простой эквивалент через `COUNTUNIQUEIFS` (Google Sheets):

```
=COUNTUNIQUEIFS($D$2:$D$999, $G$2:$G$999, $G2)
```

### Суммарная занятость сотрудника (для поиска перегруза)

```
=SUMIF($G:$G, $G2, $I:$I)
```

Значение > 1 означает, что человек расписан больше чем на 100% — либо реальный перегруз, либо ошибка в долях. И то и другое надо увидеть.

### Зарплата непосредственного руководителя (для поиска инверсий)

```
=IFERROR(VLOOKUP($C2, {$G:$G, $H:$H}, 2, FALSE), "")
```

Даёт возможность подсветить случаи, когда подчинённый зарабатывает больше руководителя.

### Составной ключ продукта

Названия продуктов могут повторяться в разных проектах («Личный кабинет» может быть и там и там). Чтобы `COUNTD` не склеивал их:

```
=$D2 & " / " & $E2
```

### Стаж в месяцах (если есть дата найма)

```
=DATEDIF($K2, TODAY(), "M")
```

## 1.5. Проверки перед загрузкой (сделать один раз, сэкономит часы)

| Проверка | Формула / действие | Норма |
|---|---|---|
| Сумма долей по каждому человеку = 1 | `=SUMIF(G:G, G2, I:I)` | 0.95–1.05 |
| Нет пустых ЗП | `=COUNTBLANK(H2:H999)` | 0 |
| Нет пустых ролей | `=COUNTBLANK(F2:F999)` | 0 |
| Одна ЗП на человека | `=COUNTUNIQUEIFS(H:H, G:G, G2)` | всегда 1 |
| Один ответственный на проект | `=COUNTUNIQUEIFS(B:B, D:D, D2)` | всегда 1 |
| Ровно 12 проектов | `=COUNTUNIQUE(D2:D999)` | 12 |
| Роли из справочника | Проверка данных → список | нет «прочего» |
| Нет дублей назначений | `=COUNTIFS(G:G,G2, D:D,D2, E:E,E2)` | всегда 1 |

Все эти проверки продублированы на вкладке «Качество данных» самого дашборда (см. `03-charts.md`, раздел 6) — но лучше поймать их до загрузки.

## 1.6. Где хранить данные

| Вариант | Плюсы | Минусы | Кому |
|---|---|---|---|
| **Google Sheets → коннектор DataLens** | Правки видны в дашборде почти сразу, ничего не надо разворачивать | Зависимость от Google; при >10k строк тормозит | **Рекомендую на старте** |
| **Загрузка файла (CSV/XLSX) в DataLens** | Полностью внутри Яндекса, ничего снаружи | Обновление = ручная перезаливка | Если Google принципиально нельзя |
| **Yandex Managed ClickHouse / PostgreSQL** | История срезов, скорость, RLS на уровне БД | Нужен человек, который это поддержит, и деньги | Когда дойдёте до ежемесячных снимков и 12+ месяцев истории |

**Практичный маршрут:** старт на Google Sheets → когда накопится 6+ месячных срезов и появится потребность в динамике, переезд на Managed PostgreSQL. Дашборд при переезде не переделывается: меняется только подключение в датасете, чарты остаются.

## 1.7. Про историю (сделайте это сразу, потом будет поздно)

Добавьте столбец **`Дата среза`** и заполните текущей датой (например, `2026-08-01`). Дальше — раз в месяц:

1. Копируете лист целиком в лист-архив `snapshots`.
2. Меняете `Дата среза` на новый месяц.
3. Правите то, что изменилось.

Через 3 месяца у вас появляется то, чего плоская таблица не даёт никогда:

- динамика ФОТ по проектам (и понимание, откуда взялся рост);
- история пересмотров ЗП по каждому человеку;
- текучка: кто был в срезе N и пропал в N+1;
- скорость роста команд против скорости роста результата — то самое «стало ли эффективнее».

Стоимость решения — один столбец и 5 минут в месяц. Отдача — вся аналитика динамики, которую иначе придётся восстанавливать по памяти.
