## Часть A. Общие правила оформления

Эти правила важнее любого отдельного чарта: именно они отличают дашборд, которым пользуются, от дашборда, который открыли один раз.

### A.1. Компоновка страницы

```
┌──────────────────────────────────────────────────────────────────────┐
│  Заголовок вкладки + одна строка «что здесь смотреть»                │
├──────────────────────────────────────────────────────────────────────┤
│  ПАНЕЛЬ ФИЛЬТРОВ — одна строка, общая на всю вкладку                 │
│  [Проект ▾] [Продукт ▾] [Функция ▾] [Грейд ▾] [Тип занятости ▾]     │
├──────────────────────────────────────────────────────────────────────┤
│  РЯД KPI — 4–6 плиток, ничего кроме числа, подписи и дельты          │
├──────────────────────────────────────────────────────────────────────┤
│  ГЛАВНЫЙ ЧАРТ вкладки — на всю ширину, отвечает на вопрос вкладки    │
├───────────────────────────────┬──────────────────────────────────────┤
│  Разрез 1                     │  Разрез 2                            │
├───────────────────────────────┴──────────────────────────────────────┤
│  ТАБЛИЦА-РЕЕСТР — детализация, из которой можно выгрузить в Excel    │
└──────────────────────────────────────────────────────────────────────┘
```

Три правила, которые нарушают чаще всего:

1. **Фильтры — одной строкой сверху, общие для всей вкладки.** Не внутри карточек чартов. Пользователь должен один раз выбрать срез и увидеть, как перестроилось всё.
2. **Каждая вкладка отвечает на один вопрос.** Вопрос написан текстом в подзаголовке. Если чарт не помогает ответить на этот вопрос — он на другой вкладке.
3. **Сверху вниз — от «сколько» к «кто именно».** Заканчивается всегда таблицей с фамилиями: любой вывод должен доводиться до конкретного человека, иначе по нему нельзя действовать.

### A.2. Палитра (проверена валидатором)

DataLens позволяет завести собственные палитры в настройках воркбука. Заведите три.

**Категориальная — для идентичности (функции, грейды, роли).** Присваивать по порядку, никогда не «прокручивать» по кругу:

| Слот | Светлая | Тёмная | Назначение |
|---|---|---|---|
| 1 | `#2a78d6` | `#3987e5` | Разработка |
| 2 | `#eb6834` | `#d95926` | Аналитика |
| 3 | `#1baf7a` | `#199e70` | Дизайн |
| 4 | `#eda100` | `#c98500` | Тестирование |
| 5 | `#e87ba4` | `#d55181` | Менеджмент |
| 6 | `#008300` | `#008300` | Поддержка |
| 7 | `#4a3aa7` | `#9085e9` | резерв |
| 8 | `#e34948` | `#e66767` | Прочее |

Проверено: худшая соседняя пара по цветовой слепоте ΔE 9.1 (светлая) / 8.4 (тёмная) при пороге 8; худшая пара для обычного зрения 19.6 / 19.3 при пороге 15. На точечных диаграммах и «пузырьках», где рядом могут оказаться любые две категории, безопасны только **первые три слота** — дальше сворачивайте хвост в «Прочее» или разбивайте на отдельные чарты.

**Диверегирующая — для отклонения зарплаты.** Ровно **три класса цвета**, не пять:

| Класс | Светлая | Тёмная | Значение |
|---|---|---|---|
| Недоплата | `#b3261e` | `#e0564b` | Compa-ratio < 0.90 |
| Норма | `#a8a7a0` | `#8b8a84` | 0.90–1.15 |
| Переплата | `#184f95` | `#86b6ef` | > 1.15 |

> **Почему три, а не пять.** Пятиступенчатый вариант (недоплата / ниже / норма / выше / переплата) не проходит проверку: соседние ступени внутри одного «плеча» неразличимы даже при нормальном зрении (ΔE 12.8 при пороге 15), а при дальтонизме сливаются совсем. Три класса проходят с большим запасом: ΔE 18.9 при дальтонизме и 28.6 при нормальном зрении в светлой теме. **Пятиуровневая градация никуда не девается** — она остаётся в тексте бейджа, в иконке и в самом числе Compa-ratio. Просто цвет её не несёт: цвет отвечает за «в какую сторону», текст — за «насколько».

Серый «Норма» на светлом фоне даёт контраст 2.35:1 — ниже 3:1. Это допустимо ровно потому, что бейдж всегда идёт с текстовой подписью, а не одним кружком. Без подписи так делать нельзя.

**Последовательная — для тепловых карт (загрузка, ФОТ в сводных таблицах).** Один синий тон, светлый → тёмный:

`#cde2fb → #9ec5f4 → #6da7ec → #3987e5 → #2a78d6 → #256abf → #184f95`

Никаких радуг «зелёный–жёлтый–красный» на непрерывной шкале.

### A.3. Отдельно: не раскрашивайте 12 проектов в 12 цветов

Это главная ошибка, которая ждёт вас в этом конкретном дашборде. Категориальных цветов, которые человек различает надёжно, максимум восемь. Двенадцать проектов — это гарантированно неразличимые пары, и легенда на пол-экрана.

Как правильно:

- **Столбики проектов — все одного цвета** (слот 1). Длина столбика уже кодирует величину, второй раз кодировать её цветом не нужно.
- Нужно выделить проект — **подсветите один**, остальные серым (`#c3c2b7`). Приём «emphasis» читается мгновенно.
- Нужны разные цвета — красьте по **функции** (5–6 значений) или по **флагу ЗП** (3 значения), а не по проекту.
- В древовидной карте (treemap) цвет отдайте под метрику через последовательную шкалу, а проект — под размер плитки и подпись.

### A.4. Прочее по оформлению

- **Тонкие линии, светлая сетка.** Толстые насыщенные блоки и жирная сетка визуально «кричат». Сетка — на один тон от фона.
- **Не подписывать каждую точку.** Подписывайте выборочно: крайние значения, выделенный элемент, концы линий. Остальное — по наведению.
- **Никаких двух осей Y на одном чарте.** Соотношение шкал произвольно, и чарт «показывает» корреляцию, которой нет. Нужны две метрики разного масштаба — два чарта рядом.
- **Числа — по-человечески.** ЗП — в тысячах с суффиксом (`450 тыс ₽`), а не `450000`. Проценты — с одним знаком. В DataLens это настраивается в свойствах поля (формат, точность, множитель).
- **Каждый чарт — с осмысленным заголовком-выводом.** Не «ФОТ по проектам», а «ФОТ по проектам: 62% бюджета в трёх направлениях». Заголовок в DataLens статичный, поэтому вынесите вывод в текстовый виджет рядом либо пишите нейтрально — но никогда не оставляйте чарт без объяснения, что в нём искать.
- **Тултипы дополняют, а не заменяют.** Если значение можно узнать только по наведению — его нет. Дублируйте в таблице-реестре внизу вкладки.

## Вкладка 0. Обзор компании

**Вопрос вкладки:** сколько всё это стоит, как распределено и где перекосы.
**Аудитория:** вы и собственник. Открывается по умолчанию.

### KPI-ряд (индикаторы DataLens)

| Плитка | Поле | Формат | Что должно насторожить |
|---|---|---|---|
| Сотрудников | `Сотрудников` | целое | — |
| ФОТ, мес | `ФОТ аллоц., мес` | ₽, тыс | — |
| Полная стоимость, год | `Полная стоимость, год` | ₽, млн | На 35–40% выше, чем ожидается по gross |
| Средняя / Медиана ЗП | `Средняя ЗП` и `Медианная ЗП` | ₽, тыс | Разрыв > 15% = среднее тянут несколько человек |
| FTE | `FTE` | 1 знак | Заметно меньше численности = много частичных занятостей |
| Людей на ревью ЗП | `Людей на ревью` | целое | Больше 20% штата — пороги подобраны слишком узко |
| Доля мультипроектных | `Доля мультипроектных` | % | > 40% — организация работает «матрицей» со всеми её издержками |
| Индекс полноты данных | `Индекс полноты` | % | < 90% — сначала чините данные, потом делайте выводы |

Плитки — только число, подпись и (когда появятся срезы) дельта к прошлому месяцу. Никаких мини-графиков внутри плитки: они не читаются в этом размере.

### C0.1. ФОТ и численность по проектам

- **Тип:** линейчатая (горизонтальные полосы, Bar-Y) — названия проектов длинные, на вертикальных столбцах они лягут по диагонали и станут нечитаемы.
- **Y:** `Проект` · **X:** `ФОТ аллоц., мес` · **Сортировка:** по убыванию X.
- **Цвет:** один (слот 1). Подписи на концах полос — значение ФОТ и через слэш численность: `4.2 млн / 11 чел`.
- **Зачем:** первое, что должен увидеть открывший дашборд, — куда уходят деньги. Порядок проектов по стоимости почти всегда расходится с интуитивным представлением руководителя.
- **Нюанс:** численность именно подписью, а не второй осью. Двух осей быть не должно.

### C0.2. Стоимость полной ставки по проектам

- **Тип:** линейчатая, тот же порядок проектов, что и в C0.1 (это важно — глаз сравнивает два чарта построчно).
- **X:** `Стоимость FTE` · **Референсная линия:** среднее по компании.
- **Зачем:** отвечает на вопрос, который C0.1 не отвечает: проект дорогой потому, что людей много, или потому, что люди дорогие? Два проекта одинакового размера с разницей в стоимости FTE в полтора раза — это либо разный уровень команды, либо перекос в оплате.

### C0.3. Древовидная карта «Проект → Продукт»

- **Тип:** Treemap. **Размер плитки:** `ФОТ аллоц., мес`. **Вложенность:** `Проект` → `Продукт`. **Цвет:** `Стоимость FTE` по последовательной синей шкале.
- **Зачем:** единственный чарт, где одновременно видны и структура (что во что вложено), и вес (сколько стоит), и качество (насколько дорогая команда). Крупная тёмная плитка = дорогой продукт с дорогой командой, первый кандидат на разбор.
- **Нюанс:** если продуктов больше 40, плитки станут нечитаемы — тогда только уровень проектов, а продукты через drill-down.

### C0.4. Распределение зарплат

- **Тип:** столбчатая (гистограмма). DataLens не строит гистограммы сам, поэтому нужно поле-корзина:
  ```
  Корзина ЗП = FLOOR([ЗП] / 50000) * 50000
  ```
  Ширину корзины (50 000) подберите так, чтобы получилось 8–12 столбцов.
- **X:** `Корзина ЗП` · **Y:** `COUNTD([ФИО_норм])` · **Цвет:** один.
- **Референсные линии:** медиана и среднее.
- **Зачем:** форма распределения говорит больше, чем среднее. Два горба = в компании фактически два разных рынка труда (например, продуктовая разработка и поддержка), и считать по ним одну среднюю бессмысленно. Длинный правый хвост = несколько человек определяют весь бюджет.

### C0.5. Структура ФОТ по функциям

- **Тип:** столбчатая с накоплением, 100% по ширине — одна полоса, разбитая на сегменты. Или круговая, если функций ≤ 6.
- **Сегменты:** `Функция` · **Величина:** `ФОТ аллоц., мес`.
- **Референс в подписи:** «Менеджмент: 14% (норма 10–18%)».
- **Зачем:** соотношение производящих и обеспечивающих. Ответ на вопрос «не слишком ли много у нас надстройки» — в одну секунду.
- **Нюанс:** между сегментами — зазор 2px цветом фона, не обводка. Подпись внутри сегмента только если помещается целиком, иначе выносится наружу.

### C0.6. Топ-15 самых дорогих сотрудников

- **Тип:** таблица. **Строки:** ФИО, роль, грейд, проекты (через `ALL_CONCAT([Проект], ', ')`), ЗП, Compa-ratio, бейдж флага.
- **Сортировка:** по ЗП убыв. **Фильтр:** топ-15.
- **Зачем:** конкретика. После всех агрегатов должен быть список фамилий, с которым можно идти на встречу.

## Вкладка 1. Проекты и продукты

**Вопрос вкладки:** покажи мне направление целиком — команду, стоимость, продукты, риски.
**Как работает:** сверху селектор «Проект» (одиночный выбор, по умолчанию — первый). Вся вкладка перестраивается под выбранное направление.

### Карточка направления (текстовый виджет + KPI)

Текстовый виджет с параметрами: **Ответственный**, **Руководители** (`ALL_CONCAT`), **Продуктов**, **Ролей**.
KPI: `Сотрудников` · `FTE` · `ФОТ аллоц., мес` · `Стоимость FTE` · `Средняя ЗП` · `Доля шаренных в проекте` · `Выделенных людей (100%)`.

### C1.1. Состав команды: сотрудники и их доля в проекте

- **Тип:** линейчатая с накоплением. **Y:** `ФИО` · **X:** `Доля_норм` · **Цвет:** `Функция` (категориальная палитра).
- **Сортировка:** по суммарной доле убыв.
- **Зачем:** мгновенно видно ядро команды (полные ставки) и «краешком» задействованных. Часто выясняется, что «команда из 12 человек» — это 3 полноценных и 9 по 10%.

### C1.2. Стоимость продуктов внутри направления

- **Тип:** линейчатая. **Y:** `Продукт` · **X:** `ФОТ аллоц., мес` · **Подписи:** ФОТ и FTE.
- **Цвет:** один; продукты с `Bus factor` = «Критично» подсветить статусным красным `#d03b3b` и рядом поставить иконку — цветом одним обозначать риск нельзя.
- **Зачем:** внутри направления бюджет тоже распределён неравномерно, и обычно это распределение никто не проверял.

### C1.3. Матрица «Продукт × Роль»

- **Тип:** сводная таблица с тепловой заливкой. **Строки:** `Продукт` · **Столбцы:** `Роль` (или `Функция`, если ролей больше 12) · **Значение:** `FTE` · **Заливка:** последовательная синяя.
- **Зачем:** дыры в команде видны как пустые клетки. «У продукта есть разработка, но нет ни аналитика, ни тестировщика» — типичная находка первого запуска.
- **Нюанс:** дублирующий чарт с тем же разрезом, но значением `ФОТ аллоц., мес` — та же матрица в деньгах.

### C1.4. Sankey «Проект → Роль → Сотрудник»

- **Тип:** Диаграмма Санкей. **Узлы (по порядку):** `Проект` → `Функция` → `ФИО` · **Толщина потока:** `Доля_норм`.
- **Зачем:** самый убедительный чарт для показа людям. За один взгляд читается и состав команды, и то, что часть людей приходит из других направлений. Если снять фильтр по проекту — видно всю картину пересечений между 12 направлениями.
- **Нюанс:** при снятом фильтре узлов будет много. Ограничьте средний уровень функциями (5–6), а не ролями (30+), иначе получится каша.

### C1.5. Реестр команды

Таблица: ФИО · Роль · Грейд · Доля в проекте · Общая занятость · Ещё проектов · ЗП · Compa-ratio · бейдж флага · руководитель.
Условное форматирование: `Общая занятость` > 1.1 — статусный жёлтый; бейдж — цветной markup.

## Вкладка 2. Люди и зарплаты — ядро дашборда

**Вопрос вкладки:** кому недоплачиваем, кому переплачиваем, и сколько стоит это исправить.
**Аудитория:** вы, HR, финансы. Самая чувствительная вкладка — именно её закрывают RLS.

### KPI-ряд

| Плитка | Поле |
|---|---|
| Недоплаченных (Compa < 0.9) | `COUNTD(IF [Compa-ratio] < [p_Порог_недоплаты] THEN [ФИО_норм] END)` |
| Переплаченных (Compa > 1.3) | `COUNTD(IF [Compa-ratio] > [p_Порог_переплаты] THEN [ФИО_норм] END)` |
| Статистических выбросов | `COUNTD(IF ABS([Z-score по роли]) > 2 THEN [ФИО_норм] END)` |
| **Стоимость выравнивания, мес** | `Стоимость выравнивания до порога, мес` |
| **Стоимость выравнивания, год с взносами** | `Стоимость с взносами, год` |
| Прирост ФОТ от выравнивания | `Прирост ФОТ от индексации, %` |

Две выделенные плитки — то, ради чего вкладка существует. «Чтобы не осталось недоплаченных, нужно +1.8 млн ₽ в год, это +4.1% к ФОТ» — с такой формулировкой идут к финансовому директору, а не с абстрактной справедливостью.

### C2.1. Разброс зарплат по ролям (замена box plot)

DataLens не строит «ящики с усами», поэтому собираем комбинированный чарт:

- **Тип:** комбинированная. **X:** `Роль` (отсортирована по медиане убыв.).
- **Серия 1 — точки:** `AVG([ЗП])` с детализацией до `ФИО`. Каждый сотрудник — точка. Цвет точки — трёхклассовая диверегирующая шкала по `Флаг ЗП`.
- **Серия 2 — линия:** `Медиана по роли`, толщина 2px, нейтральный тёмный.
- **Серии 3–4 — тонкие линии:** `Q1 по роли` и `Q3 по роли`, приглушённый серый.
- **Зачем:** главный диагностический чарт. Видно и уровень роли, и разброс внутри неё, и конкретных выбросов. Роль, где точки размазаны от 100k до 400k, — это либо не проставленные грейды, либо реальная проблема.
- **Нюанс:** если ролей больше 15, сделайте второй экземпляр чарта в разрезе `Роль` внутри выбранной `Функции`.

### C2.2. Compa-ratio по сотрудникам

- **Тип:** линейчатая с отклонением от 1.0. **Y:** `ФИО` · **X:** `Отклонение, %` · **Цвет:** трёхклассовая диверегирующая · **Референсная линия:** 0.
- **Сортировка:** по отклонению возр. (недоплаченные сверху — с них начинают действовать).
- **Фильтр по умолчанию:** только `Требует внимания` = 1, иначе на экране будет весь штат.
- **Зачем:** рабочий список на пересмотр, отсортированный по приоритету.
- **Нюанс:** обязательно вторая колонка — `Отклонение, ₽`. Проценты убеждают, а решение принимают по рублям: «−22%» и «−38 тыс ₽/мес» ощущаются по-разному.

### C2.3. Зарплата и стаж

*(нужен столбец «Дата найма»)*

- **Тип:** точечная. **X:** `Стаж, мес` · **Y:** `AVG([ЗП])` · **Цвет:** `Грейд` (первые 3 слота категориальной, остальные — «Прочее») · **Размер:** одинаковый.
- **Зачем:** ловит классику — «старички», которых давно не пересматривали, сидят ниже нанятых недавно на те же роли. Это самая частая причина неожиданных увольнений, и в плоской таблице её не видно.
- **Нюанс:** точки — минимум 8px, с 2px кольцом цвета фона на пересечениях. Область наведения больше самой точки.

### C2.4. Зарплата и загрузка: квадранты

- **Тип:** точечная. **X:** `Занятость сотрудника всего` · **Y:** `Compa-ratio` · **Размер пузыря:** `ЗП` · **Цвет:** `Функция`.
- **Референсные линии:** X = 1.0, Y = 1.0. Получаются четыре квадранта:

```
          Compa-ratio
              ▲
   дорогие и  │  дорогие и
   недогружен.│  загруженные
   ── разбор  │  ── всё ок
  ────────────┼────────────▶ Занятость
   недорогие и│  недорогие и
   недогружен.│  перегруженные
   ── резерв  │  ── РИСК УХОДА
              │
```

- **Зачем:** правый нижний квадрант — люди, которые тянут много и получают мало. Это ваш главный риск, и никакой отдельный чарт его так наглядно не покажет. Левый верхний — повод разобраться, чем человек занят.
- **Нюанс:** подписать точками имена только в двух «острых» квадрантах, иначе получится каша из подписей.

### C2.5. Сравнение с рынком

*(нужен справочник `dim_Рынок`)*

- **Тип:** комбинированная. **X:** `Роль` · Серия 1 — точки: `AVG([ЗП])` по сотрудникам · Серии 2–4 — линии: `Рынок P25`, `P50`, `P75`.
- **Зачем:** внутренняя справедливость и рыночная конкурентоспособность — разные вещи. Человек может быть самым высокооплачиваемым среди своих и всё равно на 30% ниже рынка. Compa-ratio этого не покажет никогда, а этот чарт — сразу.

### C2.6. Реестр сотрудников — главная таблица дашборда

Колонки: ФИО · Роль · Грейд · Функция · Проекты (`ALL_CONCAT`) · Занятость · ЗП · База сравнения · **Уровень сравнения** · Compa-ratio · Отклонение ₽ · Z-score · Выброс по IQR · **бейдж флага** · Риск ухода · Мес. с пересмотра.

- Сортировка по умолчанию: `Отклонение, ₽` возр.
- Бейдж — markup-поле `Флаг ЗП (бейдж)`.
- **Колонка «Уровень сравнения» обязательна.** Она честно говорит, на чём основан вывод: «Роль + грейд» — вывод крепкий, «Функция (мало данных)» — вывод слабый, там всего два человека в группе. Без этой колонки дашборд создаёт ложную уверенность, и первый же разбор конкретного кейса подорвёт доверие ко всему остальному.

## Вкладка 3. Загрузка и пересечения

**Вопрос вкладки:** кто размазан по проектам, кто перегружен, а кто недогружен.

### KPI-ряд

`FTE` · `Эффективный FTE` · `Потери на переключении, FTE` · **`Потери на переключении, ₽/мес`** · `Назначений на человека` · Перегруженных · Недогруженных.

Выделенная плитка — цена организационной размазанности в рублях. Обычно это число оказывается сопоставимым с зарплатой одного-двух человек, и после этого разговор про «давай подключим Петрова ещё на один проект» идёт иначе.

### C3.1. Матрица «Сотрудник × Проект»

- **Тип:** сводная таблица с тепловой заливкой. **Строки:** `ФИО` · **Столбцы:** `Проект` · **Значение:** `SUM([Доля_норм])` · **Заливка:** последовательная синяя · **Итоги:** по строкам и столбцам включить.
- **Сортировка строк:** по `Проектов у сотрудника` убыв. — сверху самые размазанные.
- **Зачем:** центральный чарт вкладки, самый «плотный» по информации на дашборде. Итог по строке = общая загрузка человека (должен быть ≈ 1). Итог по столбцу = FTE проекта.
- **Нюанс:** при 100+ сотрудниках таблица станет длинной — добавьте фильтр «только мультипроектные».

### C3.2. Перегруз и недогруз

- **Тип:** линейчатая. **Y:** `ФИО` · **X:** `Занятость сотрудника всего` · **Референсная линия:** 1.0 · **Цвет:** статусная палитра по `Статус загрузки` — с иконкой и подписью, не одним цветом.
- **Фильтр:** только те, у кого занятость вне диапазона 0.9–1.1.
- **Зачем:** двойной смысл. Перегруз — либо реальный (человек горит), либо ошибка в долях. Недогруз — либо человека недозагрузили, либо просто забыли внести назначение. И то и другое надо разобрать поштучно.

### C3.3. Мультипроектность по функциям

- **Тип:** столбчатая с накоплением. **X:** `Функция` · **Y:** `COUNTD([ФИО])` · **Цвет:** число проектов (1 / 2 / 3+ — три класса ординальной шкалы одного тона).
- **Зачем:** обычно выясняется, что размазаны в основном аналитики и дизайнеры — редкие компетенции, которые вынуждены обслуживать все направления. Это не «плохая дисциплина», а сигнал, что этих людей не хватает. Вывод из чарта — нанимать, а не «наводить порядок».

### C3.4. Пересечения проектов по людям

- **Тип:** сводная таблица. **Строки и столбцы:** `Проект` · **Значение:** число общих сотрудников · **Заливка:** последовательная.
- **Формула:** проще всего посчитать в источнике отдельным листом (самосоединение таблицы назначений по ФИО с фильтром «проект A ≠ проект B»); в DataLens отобразить готовым.
- **Зачем:** матрица «кто с кем связан людьми». Пары направлений с большим пересечением — кандидаты либо на объединение, либо на разделение команд: сейчас они конкурируют за одних и тех же людей, и любой сдвиг сроков в одном бьёт по другому.

## Вкладка 4. Оргструктура

**Вопрос вкладки:** сбалансирована ли управленческая надстройка и нет ли аномалий в иерархии.

### C4.1. Норма управляемости

- **Тип:** линейчатая. **Y:** `Руководитель` · **X:** `Span of control` · **Референсные полосы:** 5–9 (норма).
- **Цвет:** статусная палитра — < 3 «лишний уровень», 5–9 «норма», > 12 «перегружен». С подписями.
- **Зачем:** руководитель с двумя подчинёнными — обычно следствие исторических причин, а не потребности. Руководитель с пятнадцатью — тот, кто не успевает ни с кем поговорить. Оба случая стоят денег.

### C4.2. ФОТ и численность под руководителями

- **Тип:** линейчатая. **Y:** `Руководитель` · **X:** `ФОТ под руководителем` · **Подпись:** число людей и средняя ЗП команды.
- **Зачем:** масштаб ответственности в деньгах. Дальше — сопоставление с зарплатой самого руководителя.

### C4.3. Зарплата ответственного и масштаб направления

- **Тип:** точечная. **X:** `ФОТ аллоц., мес` направления · **Y:** ЗП ответственного · **Подписи:** имена всех точек (их всего 12).
- **Референс:** линия тренда, если доступна; иначе визуально.
- **Зачем:** самый прямой ответ на вопрос «оправданы ли зарплаты руководителей». Точка сильно ниже линии — человек тянет большое направление за небольшие деньги (риск). Сильно выше — маленькое направление за большие (вопрос).
- **Нюанс:** 12 точек — тот редкий случай, когда подписать можно все.

### C4.4. Инверсии в оплате

- **Тип:** таблица. **Фильтр:** `Инверсия ЗП` ≠ пусто.
- **Колонки:** сотрудник · его ЗП · руководитель · ЗП руководителя · разница · проект.
- **Зачем:** ситуация «подчинённый дороже руководителя» сама по себе не патология — сильный сеньор вполне может получать больше своего тимлида. Но это всегда должно быть осознанным решением, а не выясняться случайно. Обычно в списке оказывается 2–5 строк, и половина — сюрприз.

### C4.5. Управленческая надстройка по проектам

- **Тип:** линейчатая. **Y:** `Проект` · **X:** `Доля менеджмента в ФОТ` · **Референсная линия:** 18%.
- **Зачем:** сравнение направлений по «тяжести» управления. Проект, где на менеджмент уходит 35% ФОТ, — это либо очень сложная координация, либо структура, которую пора упростить.

## Вкладка 5. Экономика продуктов *(контур 2)*

**Вопрос вкладки:** отбивает ли продукт свою команду.
**Требует:** справочник `templates/products_template.csv` с метрикой результата.

### C5.1. Квадрант «стоимость — отдача»

- **Тип:** точечная. **X:** `Полная стоимость, мес` · **Y:** `Выручка продукта` (или MAU / другая метрика) · **Размер:** `FTE` · **Цвет:** `Стадия продукта` (первые 3 слота + «Прочее»).
- **Референс:** диагональ окупаемости (Y = X).
- **Зачем:** главный чарт вкладки. Продукты ниже диагонали не окупают собственную команду. Но читать это надо с поправкой на стадию: MVP ниже диагонали — норма, mature ниже диагонали — вопрос.

### C5.2. Cost ratio по продуктам

- **Тип:** линейчатая. **Y:** `Продукт_ключ` · **X:** `Cost ratio (ФОТ/выручка)` · **Референсная линия:** 100% · **Цвет:** статусный по `Окупаемость команды`, с подписями.

### C5.3. Выручка на FTE

- **Тип:** линейчатая. **Y:** `Продукт_ключ` · **X:** `Выручка на FTE` · **Референс:** среднее по компании.
- **Зачем:** нормирует на размер команды и позволяет честно сравнить большой продукт с маленьким.

### C5.4. Динамика (когда накопятся срезы)

- **Тип:** линейная, одна ось. **X:** `Месяц среза` · **Серии:** ФОТ продукта и выручка продукта, **обе индексированы к 100 на первом месяце**.
- **Зачем:** отвечает на вопрос «стало ли эффективнее» — расходящиеся линии видны сразу.
- **Нюанс:** индексация к общей базе — именно тот приём, который позволяет положить две метрики разного масштаба на один чарт, не заводя вторую ось.

## Вкладка 6. Качество данных

**Вопрос вкладки:** можно ли верить всему предыдущему.

Служебная вкладка, но открывать её надо первой при каждом обновлении данных. Дашборд, который однажды показал ерунду из-за опечатки, теряет доверие навсегда — а на этой вкладке ерунда ловится за минуту.

### KPI

`Индекс полноты` · Строк без ЗП · Строк без роли · Людей без грейда · Людей с битой долей · Людей с разными ЗП в строках · Проектов с несколькими ответственными · Дублей назначений.

Все должны быть нулями (кроме индекса полноты — он должен быть 100%).

### C6.1. Заполненность по столбцам

- **Тип:** линейчатая. **Y:** название проверки · **X:** число проблемных строк · **Цвет:** статусный (0 — зелёный, > 0 — красный), с подписями.

### C6.2. Проблемные строки

- **Тип:** таблица со всеми строками, где сработала хотя бы одна проверка. Колонка «Тип проблемы» — конкатенация сработавших флагов:
  ```
  CONCAT(
    IF [Нет ЗП] = 1 THEN 'нет ЗП; ' ELSE '' END,
    IF [Нет роли] = 1 THEN 'нет роли; ' ELSE '' END,
    IF [Нет грейда] = 1 THEN 'нет грейда; ' ELSE '' END,
    IF [Битая доля] = 1 THEN 'сумма долей ≠ 1; ' ELSE '' END,
    IF [Разные ЗП у одного ФИО] = 1 THEN 'разные ЗП у одного человека; ' ELSE '' END,
    IF [Дубль назначения] = 1 THEN 'дубль; ' ELSE '' END
  )
  ```
- **Зачем:** это не отчёт, а список задач. Прошли по списку, поправили в источнике, обновили — вкладка пустая.

### C6.3. Сверка итогов

Небольшая таблица на три строки, сравнивающая метрики, посчитанные разными способами:

| Метрика | Способ 1 | Способ 2 | Совпадает |
|---|---|---|---|
| Численность | `COUNTD([ФИО_норм])` | `SUM([Первичное])` | должны совпасть |
| ФОТ | `ФОТ аллоц., мес` | `ФОТ уник., мес` | должны совпасть |
| Проектов | `COUNTD([Проект])` | 12 (константа) | должны совпасть |

Если способы расходятся — где-то поехали доли или дубли. Это самая дешёвая страховка от тихой ошибки в цифрах, которую иначе замечают через полгода.
