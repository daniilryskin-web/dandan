# 06. Полная инструкция по сборке дашборда в DataLens

Документ описывает дашборд **под конкретный датасет**, который выдаёт `prepare_dataset.py`. Это рабочая инструкция: открываете её рядом с DataLens и собираете сверху вниз.

Файл `03-charts.md` писался по описанию таблицы и местами устарел. **Где они расходятся, верен этот файл.**

---

## Часть 0. Подготовка

### 0.1. Получить датасет

Положите выгрузку рядом со скриптом под именем **`Datalens.xlsx`** и запустите:

```bash
python3 prepare_dataset.py --snapshot 2026-08-01
```

Больше ничего указывать не нужно. Лист с данными скрипт находит сам — берёт первый, где есть все обязательные столбцы, и печатает его имя. Служебные листы (сводные, справочники) при этом пропускаются, даже если стоят в книге первыми.

Если файл называется иначе или лежит в другом месте — путь передаётся первым аргументом, а лист можно задать явно:

```bash
python3 prepare_dataset.py "другая_выгрузка.xlsx" --sheet "Поправлено (Как будет)"
```

Скрипт печатает 17 проверок, контроль монотонности медиан по уровням ролей и сводку по светофору. **Пока не увидели «Монотонность: ОК» — дальше не идите:** это значит, что классификация ролей нарушена и откат на уровень будет искажать базу сравнения.

На выходе `datalens_dataset.csv` — его и грузим. Что означает каждый лист и каждый столбец — в [`07-dataset-reference.md`](07-dataset-reference.md).

### 0.2. Подключение и датасет

1. **Подключения → создать → Файлы** → загрузить `datalens_dataset.csv`. Кодировка UTF‑8, разделитель — запятая, первая строка — заголовки.
2. **Датасеты → создать** → выбрать подключение → добавить таблицу.
3. Проверить типы полей. DataLens определяет их сам, но три места стоит посмотреть:

| Поле | Должно быть | Почему это важно |
|---|---|---|
| `Сотрудник` | Строка | Иначе идентификаторы поедут как «176.0» на всех подписях |
| `Дата среза` | Дата | Понадобится, когда накопятся месячные срезы |
| `Уровень роли №`, `Вакансия`, `Первичное назначение`, `ЗП подтверждена`, `В анализе справедливости`, `Требует внимания` | Целое | Это флаги и порядковые номера, по ним считаются суммы и сортировки |

### 0.3. Форматы отображения

Настраивается в свойствах поля. Сделать один раз — иначе чарты будут пестрить числами вида `31692786.0`.

| Поля | Формат |
|---|---|
| `ЗП`, `ФОТ аллоцированный`, `База сравнения`, `Отклонение руб`, `Доплата до порога`, `Оценка стоимости вакансии`, все медианы и квартили | Число, разделитель разрядов, 0 знаков, префикс «₽» |
| `Compa-ratio` | Число, 2 знака |
| `Доля занятости` | Число, 2 знака |
| `Z-score` | Число, 2 знака |

### 0.4. Иерархия для drill-down

Датасет → **Поля → создать иерархию**:

```
Организационная:  Блок → Проект → Продукт → Проектная роль → Сотрудник
```

Клик по столбцу блока проваливает в его проекты, дальше в продукты. Это заменяет три селектора и сильно упрощает вкладку 0.

## Часть 1. Вычисляемые поля в датасете

Большая часть расчётов уже сделана скриптом. В DataLens добавляем только то, что зависит от параметров и от разреза чарта.

### 1.1. Параметры

Датасет → вкладка **«Параметры»**.

| Параметр | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `p_Взносы` | Дробное | `0.302` | Страховые взносы. Для аккредитованных IT — `0.076` |
| `p_Накладные` | Целое | `15000` | Рабочее место, техника, ДМС на человека в месяц |
| `p_Индексация` | Целое | `10` | % повышения для what-if сценария |

Параметры выводятся на дашборд селекторами типа «Ввод». Пользователь крутит их сам и видит, как меняются цифры — это сильно повышает доверие к дашборду.

### 1.2. Поля

Создаются на вкладке **«Поля»**. Порядок важен: поля ссылаются на предыдущие.

**Численность и объём**

```
Сотрудников          = COUNTD([Сотрудник]) - COUNTD(IF [Вакансия] = 1 THEN [Сотрудник] END)
```
Проще и надёжнее — через флаг первичного назначения:
```
Сотрудников          = SUM([Первичное назначение])
Открытых вакансий    = SUM([Вакансия])
Назначений           = COUNT([Строка])
FTE                  = SUM(IF [Вакансия] = 0 THEN [Доля занятости] ELSE 0 END)
FTE вакансий         = SUM(IF [Вакансия] = 1 THEN [Доля занятости] ELSE 0 END)
Продуктов            = COUNTD([Продукт ключ])
Проектов             = COUNTD([Проект])
```

> **Почему `SUM([Первичное назначение])`, а не `COUNTD([Сотрудник])`.** Оба верны, но первое считается быстрее и переживает любые разрезы. Единственная тонкость: если в чарте стоит фильтр по проекту, «первичной» может оказаться строка из другого проекта, и человек не посчитается. Поэтому: **на вкладке 0 (общие итоги) — `SUM([Первичное назначение])`, на вкладках с фильтром по проекту — `COUNTD([Сотрудник])`.** Оба поля заведите сразу, назовите `Сотрудников (всего)` и `Сотрудников (в срезе)`.

**Деньги**

```
ФОТ, мес             = SUM([ФОТ аллоцированный])
ФОТ, год             = [ФОТ, мес] * 12
Полная стоимость мес = [ФОТ, мес] * (1 + [p_Взносы]) + [p_Накладные] * [FTE]
Полная стоимость год = [Полная стоимость мес] * 12
Стоимость FTE        = [ФОТ, мес] / [FTE]
Средняя ЗП           = SUM(IF [Первичное назначение] = 1 THEN [ЗП] ELSE 0 END)
                       / SUM([Первичное назначение])
Медианная ЗП         = MEDIAN(IF [Первичное назначение] = 1 THEN [ЗП] END)
Разрыв среднее/медиана = [Средняя ЗП] / [Медианная ЗП]
Доля ФОТ от общего   = [ФОТ, мес] / SUM([ФОТ аллоцированный] TOTAL)
```

**Вакансии**

```
Стоимость вакансий мес = SUM([Оценка стоимости вакансии])
Стоимость вакансий год = [Стоимость вакансий мес] * 12
Прирост ФОТ при найме  = [Стоимость вакансий мес] / [ФОТ, мес]
```

**Справедливость оплаты**

База сравнения — медиана по **проектной роли**, то есть по фактически выполняемой работе. Штатная должность в расчётах не участвует вообще: её могли назначить формально, чтобы обосновать оклад. Обоснование — `05-adaptation.md`, §3.5; должность и организация остаются справочными колонками в реестре.

```
Людей в анализе      = SUM([В анализе справедливости])
Людей на ревью       = SUM([Требует внимания])
Людей на ревью (подтв.) = SUM(IF [ЗП подтверждена] = 1 THEN [Требует внимания] ELSE 0 END)

Недоплачивают        = SUM(IF [Группа оценки] = 'Недоплата' THEN 1 ELSE 0 END)
Соответствует роли   = SUM(IF [Группа оценки] = 'Соответствует роли' THEN 1 ELSE 0 END)
Переплачивают        = SUM(IF [Группа оценки] = 'Переплата' THEN 1 ELSE 0 END)
Доля справедливых, % = [Соответствует роли] / [Людей в анализе]

Сумма недоплаты, год = SUM(IF [Отклонение руб] < 0 THEN [Отклонение руб] ELSE 0 END) * 12
Сумма переплаты, год = SUM(IF [Отклонение руб] > 0 THEN [Отклонение руб] ELSE 0 END) * 12
Подтверждены двумя методами = SUM(
  IF [Требует внимания] = 1 AND [Выброс по IQR] <> 'В норме' THEN 1 ELSE 0 END)

Выравнивание, мес       = SUM([Доплата до порога])
Выравнивание, год       = [Выравнивание, мес] * 12
Выравнивание с взносами = [Выравнивание, год] * (1 + [p_Взносы])
Прирост ФОТ от выравнивания = [Выравнивание, мес] / [ФОТ, мес]
```

**Три сценария выравнивания.** Столбец `Сценарий выравнивания` делит людей на вложенные группы, поэтому каждый сценарий — это сумма по своему набору значений:

```
Сценарий A · минимум = SUM(
  IF [Сценарий выравнивания] = '1. Недоплата, ЗП подтверждена'
  THEN [Доплата до порога] ELSE 0 END)

Сценарий B · подтверждённые = SUM(
  IF [Сценарий выравнивания] IN ('1. Недоплата, ЗП подтверждена',
                                 '2. Ниже роли, ЗП подтверждена')
  THEN [Доплата до порога] ELSE 0 END)

Сценарий C · верхняя оценка = SUM([Доплата до порога])

Людей в сценарии A = COUNTD(
  IF [Сценарий выравнивания] = '1. Недоплата, ЗП подтверждена'
  THEN [Сотрудник] END)
```

`Доплата до порога` лежит только на первичном назначении, поэтому `SUM` не задваивает людей с несколькими продуктами — дополнительный фильтр не нужен.

- **Чарт:** три столбца рядом (A / B / C), подпись — цена в год и число людей.
- **Зачем.** Одна цифра «выравнивание стоит 22 млн» вызывает спор о самой цифре. Три сценария переводят разговор в выбор: 8,9 млн за 13 человек, 11,0 за 24, 22,2 за 41 — и последний требует сначала уточнить зарплаты.
- **Нюанс.** A даёт 80% стоимости B при половине людей. Если это соотношение сохранится и на ваших обновлённых данных — начинать надо с A, и это следует сказать прямо в подписи к чарту.

**What-if индексация**

```
ФОТ после индексации = SUM(
  IF [Требует внимания] = 1 AND [Compa-ratio] < 1
  THEN [ФОТ аллоцированный] * (1 + [p_Индексация] / 100)
  ELSE [ФОТ аллоцированный] END
)
Стоимость сценария   = [ФОТ после индексации] - [ФОТ, мес]
```

**Качество данных**

```
Доля подтверждённых ЗП = SUM(IF [Первичное назначение] = 1 THEN [ЗП подтверждена] ELSE 0 END)
                         / SUM([Первичное назначение])
Продуктов с 1 человеком = COUNTD(IF [Bus factor] = 'Критично: 1 человек' THEN [Продукт ключ] END)
```

**Оформление**

```
Бейдж оценки = CASE [Оценка ЗП]
  WHEN '1. Недоплата'          THEN COLOR(BOLD('▼▼ Недоплата'),   '#b3261e')
  WHEN '2. Ниже роли'          THEN COLOR('▼ Ниже роли',          '#b3261e')
  WHEN '3. Соответствует роли' THEN COLOR('● Соответствует роли', '#52514e')
  WHEN '4. Выше роли'          THEN COLOR('▲ Выше роли',          '#184f95')
  WHEN '5. Переплата'          THEN COLOR(BOLD('▲▲ Переплата'),   '#184f95')
  ELSE COLOR('— не оценивается', '#898781') END

Метка выброса = IF [Выброс по IQR] <> 'В норме' AND [Выброс по IQR] <> '—'
  THEN COLOR('⧫ выброс', '#eb6834') ELSE '' END

Метка достоверности = IF [ЗП подтверждена] = 0
  THEN COLOR('⚠ ЗП не подтверждена', '#b3261e') ELSE '' END

Корзина ЗП = FLOOR([ЗП] / 50000) * 50000
```

## Часть 2. Палитры

Создаются в настройках воркбука (**Палитры → создать**). Три штуки.

**«Категориальная»** — для идентичности: блоки, организации, проектные роли.
```
#2a78d6  #eb6834  #1baf7a  #eda100  #e87ba4  #008300  #4a3aa7  #e34948
```
Проверено на различимость при дальтонизме. Максимум 8 значений; на точечных диаграммах безопасны первые три.

**«Оценка ЗП»** — ровно три цвета:
```
Недоплата #b3261e   Соответствует роли #a8a7a0   Переплата #184f95
```
Привязывается к полю `Группа оценки` (не к `Оценка ЗП` — там пять значений, а пять цветовых классов человек надёжно не различает). Цвет несёт направление, текст — степень.

**«Уровни ролей»** — порядковая шкала на пять ступеней, один синий тон светлый → тёмный:
```
R0 #86b6ef   R1 #5598e7   R2 #2a78d6   R3 #1c5cab   R4 #0d366b
```
Привязывается к `Уровень роли`. Уровень — упорядоченная шкала, красить её категориальными цветами нельзя. Проверено валидатором: монотонная по светлоте, шаги различимы, светлый конец читается на белом фоне.

### Правило, которое здесь легче всего нарушить

**Не раскрашивайте 12 проектов в 12 цветов.** Надёжно различимых категориальных цветов максимум восемь. Столбики проектов делаются **одним** цветом — их длина уже кодирует величину. Нужен акцент — подсветите один проект, остальные серым `#c3c2b7`. Нужны разные цвета — красьте по блоку (4 значения), уровню роли (5, порядковой шкалой) или флагу ЗП (3).

## Часть 3. Вкладки и чарты

Общая компоновка каждой вкладки:

```
Заголовок + одна строка «что здесь смотреть»
─────────────────────────────────────────────
Строка селекторов — общая на всю вкладку
─────────────────────────────────────────────
Ряд KPI-индикаторов

Главный чарт вкладки, на всю ширину
```

# Вкладка 0 — Обзор

**Вопрос:** сколько всё это стоит и где перекосы.

**Селекторы:** `Блок` · `Организация` · `Уровень роли`

### KPI-ряд (тип чарта «Индикатор»)

| № | Плитка | Поле | Ожидаемое значение |
|---|---|---|---|
| 1 | Сотрудников | `Сотрудников (всего)` | 180 |
| 2 | Открытых вакансий | `Открытых вакансий` | 35 |
| 3 | ФОТ, мес | `ФОТ, мес` | 31.7 млн ₽ |
| 4 | Полная стоимость, год | `Полная стоимость год` | ≈ 528 млн ₽ |
| 5 | Средняя / медианная ЗП | два индикатора рядом | 176 / 135 тыс ₽ |
| 6 | FTE | `FTE` | 180 |
| 7 | Стоимость вакансий, год | `Стоимость вакансий год` | 70 млн ₽ |
| 8 | Доля подтверждённых ЗП | `Доля подтверждённых ЗП` | 68% |

Плитка 4 обычно удивляет сильнее всех: полная стоимость на треть выше того, что видно в столбце зарплат. Плитка 7 отвечает на вопрос, который в таблице не задан вовсе — «во сколько обойдётся закрыть набор» (+18% к ФОТ). Плитка 8 — индикатор доверия ко всему остальному.

### C0.1 — ФОТ по проектам

- **Тип:** Линейчатая (горизонтальные полосы). Названия проектов длинные, на вертикальных столбцах лягут по диагонали.
- **Y:** `Проект` · **X:** `ФОТ, мес` · **Сортировка:** X по убыванию
- **Цвет:** один, слот 1
- **Подписи:** значение
- **Зачем.** Первое, что видит открывший дашборд. Порядок направлений по стоимости почти всегда расходится с интуитивным представлением. Численность сюда **не добавляйте второй осью** — двух осей Y на чарте быть не должно, соотношение шкал произвольно и чарт начинает «показывать» корреляцию, которой нет.

### C0.2 — Стоимость полной ставки по проектам

- **Тип:** Линейчатая, **тот же порядок проектов, что в C0.1** — глаз сравнивает два чарта построчно
- **Y:** `Проект` · **X:** `Стоимость FTE`
- **Референсная линия:** среднее по компании (≈ 176 тыс)
- **Зачем.** Отвечает на вопрос, который C0.1 не отвечает: проект дорогой потому, что людей много, или потому что люди дорогие. На ваших данных разброс от 124 до 246 тыс — двукратный, и он отражает разный состав ролей, а не разные ставки.

### C0.3 — Древовидная карта «Проект → Продукт»

- **Тип:** Древовидная (Treemap)
- **Разбивка:** `Проект`, затем `Продукт` · **Размер:** `ФОТ, мес` · **Цвет:** `Стоимость FTE`, палитра «Уровни ролей» как последовательная
- **Зачем.** Единственный чарт, где одновременно видны структура (что во что вложено), вес (сколько стоит) и качество (насколько дорогая команда). Крупная тёмная плитка — дорогой продукт с дорогой командой, первый кандидат на разбор.
- **Нюанс.** 57 продуктов — многовато для одного экрана. Ограничьте до уровня проектов, а продукты открывайте через drill-down.

### C0.4 — Структура ФОТ по уровням ролей

- **Тип:** Столбчатая с накоплением, нормированная на 100%. Одна полоса на весь экран, разбитая на сегменты
- **Разбивка:** `Уровень роли` · **Значение:** `ФОТ, мес` · **Цвет:** палитра «Уровни ролей»
- **Сортировка:** по `Уровень роли №`
- **Зачем.** Соотношение уровней ответственности в деньгах. На ваших данных R4 — руководство проектами — съедает непропорционально большую долю ФОТ относительно своей численности.
- **Нюанс.** Между сегментами — зазор 2 px цветом фона, не обводка. Подпись внутри сегмента только если помещается целиком, иначе выносится наружу.

### C0.5 — Матрица «Уровень роли × Проект»

- **Тип:** Сводная таблица с тепловой заливкой
- **Строки:** `Уровень роли` (сортировка по `Уровень роли №`) · **Столбцы:** `Проект` · **Значение:** `Сотрудников (в срезе)` · **Заливка:** последовательная синяя
- **Итоги:** включить по строкам и столбцам
- **Зачем.** Структура штата — на мой взгляд, самая содержательная картинка во всём дашборде. Сразу видно, что доля начальных уровней по проектам гуляет от 0% до 68%: часть направлений укомплектована дорогими позициями целиком, часть держится на стажёрах и специалистах. Это разговор не про зарплаты, а про то, как устроены команды.
- **Второй экземпляр** того же чарта со значением `ФОТ, мес` — та же матрица в деньгах.

### C0.6 — Распределение зарплат

- **Тип:** Столбчатая (гистограмма). DataLens не строит гистограммы сам, поэтому нужен разрез `Корзина ЗП`
- **X:** `Корзина ЗП` · **Y:** `Сотрудников (в срезе)` · **Фильтр:** `Первичное назначение` = 1
- **Референсные линии:** медиана и среднее
- **Зачем.** Форма распределения говорит больше, чем среднее. На ваших данных распределение многогорбое — это прямое следствие тарифной сетки: масса людей стоит ровно на ступенях 31/72/120/250/350 тыс. Средняя по такому распределению почти бессмысленна, и чарт это показывает наглядно.

### C0.7 — Вакансии

- **Тип:** Линейчатая
- **Y:** `Проектная роль` · **X:** `Открытых вакансий` · **Фильтр:** `Вакансия` = 1
- **Подписи:** количество и `Стоимость вакансий мес`
- **Зачем.** Две трети открытых позиций приходятся на две роли — это показывает, где идёт активный набор, и одновременно даёт прогноз прироста ФОТ.

### C2.1 — Разброс зарплат по проектным ролям *(замена box plot)*

DataLens не строит «ящики с усами», поэтому собираем комбинированный чарт из четырёх серий.

- **Тип:** Комбинированная
- **X:** `Проектная роль` (сортировка по `Уровень роли №`)
- **Серия 1, точки:** `ЗП`, детализация до `Сотрудник`. Цвет точки — `Группа оценки`, палитра «Оценка ЗП»
- **Серия 2, линия:** `MEDIAN([ЗП])`, толщина 2 px, нейтральный тёмный — это и есть база сравнения
- **Серии 3–4, тонкие линии:** `QUANTILE([ЗП], 0.25)` и `QUANTILE([ЗП], 0.75)`, приглушённый серый
- **Фильтр:** `В анализе справедливости` = 1
- **Зачем.** Главный диагностический чарт: сколько платят за конкретную работу и кто из этого выбивается. На ваших данных роль «Администратор проекта» растянута от 31 тыс до 251 тыс — восьмикратно при медиане 120 тыс. Одна и та же работа, восьмикратная разница в оплате: с этого чарта начинается любой разбор.
- **Нюанс.** Точки минимум 8 px, с кольцом 2 px цветом фона на пересечениях. Область наведения должна быть больше самой точки.

### C2.2 — Compa-ratio по сотрудникам

- **Тип:** Линейчатая
- **Y:** `Сотрудник` · **X:** `Отклонение руб` · **Цвет:** `Группа оценки` · **Референсная линия:** 0
- **Сортировка:** X по возрастанию — недоплаченные сверху, с них и начинают
- **Фильтр по умолчанию:** `Требует внимания` = 1
- **Зачем.** Рабочий список на пересмотр, отсортированный по приоритету.
- **Нюанс.** Ось именно в рублях, а не в процентах. Проценты убеждают, а решение принимают по деньгам: «−22%» и «−130 тыс ₽/мес» ощущаются совершенно по-разному. Compa-ratio показывайте в подсказке.

### C2.3 — Оценка зарплат: сколько кого

- **Тип:** Линейчатая с накоплением, одна полоса на всю ширину
- **Разбивка:** `Оценка ЗП` (сортировка по значению — цифровой префикс это обеспечивает) · **Значение:** `Сотрудников (в срезе)`
- **Цвет:** «1. Недоплата» и «2. Ниже роли» — красные `#b3261e` разной насыщенности, «3. Соответствует роли» — серый `#a8a7a0`, «4. Выше роли» и «5. Переплата» — синие `#184f95`
- **Подписи:** количество и процент
- **Фильтр:** `В анализе справедливости` = 1
- **Зачем.** Одна картинка, отвечающая на вопрос вкладки: 25 недоплаченных, 14 ниже роли, 99 соответствуют, 7 выше, 11 переплачено. Ставьте её сразу под KPI-рядом.
- **Обязательно рядом** — тот же разрез в деньгах: `SUM([Отклонение руб])` по категориям. Числа людей и суммы отклонений расходятся: переплаченных вдвое меньше, но переплата на человека крупнее.

### C2.3б — Оценка по ролям: где перекос системный

- **Тип:** Сводная таблица с тепловой заливкой
- **Строки:** `Проектная роль` (сортировка по `Уровень роли №`) · **Столбцы:** `Оценка ЗП` · **Значение:** `Сотрудников (в срезе)` · **Итоги:** включить
- **Зачем.** Отделяет индивидуальные случаи от системных. У руководителей продукта 9 недоплаченных и 5 «ниже роли» из 39 — больше трети роли оплачивается ниже её же медианы, и это уже не про отдельных людей, а про то, как в компании принято платить за эту работу.
- **Второй экземпляр** с разрезом по `Проект` вместо роли — показывает направления, где недоплата или переплата концентрируется.

### C2.3в — Согласие двух методов *(проверочный)*

- **Тип:** Сводная таблица
- **Строки:** `Группа оценки` · **Столбцы:** `Выброс по IQR` · **Значение:** `Сотрудников (в срезе)`
- **Зачем.** Compa-ratio и правило IQR — два независимых способа найти выброс. Клетки, где они сошлись, — самые надёжные случаи: 12 человек с переплатой и 14 с недоплатой. Клетка «Соответствует роли × Выброс вверх» (23 человека) — те, кто внутри порогов, но статистически необычен для своей роли; их стоит посмотреть вторым заходом.
- **Нюанс.** Не сводите два метода в один флаг. Расхождение между ними — это информация, а не шум.

### C2.4 — Квадрант «зарплата × загрузка»

- **Тип:** Точечная
- **X:** `Продуктов у сотрудника` · **Y:** `Compa-ratio` · **Размер:** `ЗП` · **Цвет:** `Уровень роли`
- **Референсные линии:** X = 1, Y = 1
- **Зачем.** Правый нижний квадрант — люди на нескольких продуктах с зарплатой ниже своей группы. Это главный риск ухода, и никакой другой чарт не покажет его так наглядно.
- **Нюанс.** Подписывать точки только в двух «острых» квадрантах, иначе получится каша.

### C2.5 — Зарплаты по организациям *(контрольный чарт)*

- **Тип:** Комбинированная. **X:** `Проектная роль` · **Серия-точки:** `MEDIAN([ЗП])` с разбивкой по `Организация`
- **Зачем.** Это проверка, а не аналитика. Разбор показал, что медианы внутри одной роли по организациям совпадают — действует единая тарифная сетка. Чарт нужен, чтобы это было видно, и чтобы заметить, если однажды перестанет совпадать: расхождение будет означать, что одна из организаций начала платить по другим правилам.

### C2.6 — Реестр сотрудников *(главная таблица дашборда)*

Колонки в этом порядке:

**`Сотрудник`** · **`Проектная роль`** · `Уровень роли` · `ЗП` · `База сравнения` · **`Уровень сравнения`** · `Compa-ratio` · `Отклонение руб` · `Z-score` · **`Бейдж оценки`** · **`Метка выброса`** · **`Метка достоверности`** · `Доплата до порога` · `Организация` · `Штатная должность` · `Проект` · `Руководитель`

Порядок колонок не случаен: сначала роль и всё, что считается от неё, и только потом справочные организация с должностью. Читается как «за эту работу платят столько → а этому человеку столько → отсюда отклонение».

- Сортировка по умолчанию: `Отклонение руб` по возрастанию
- Условное форматирование на `Compa-ratio`: диверегирующая шкала

> **Колонка «Уровень сравнения» обязательна.** Она честно говорит, на чём основан вывод: «Проектная роль» — вывод крепкий (153 человека), «Уровень роли (мало данных)» — выборка мала (3 человека: роли «Аналитик» и «Руководитель функции»). Без неё дашборд создаёт ложную уверенность, и первый же разбор конкретного кейса подорвёт доверие ко всему остальному.

> **Штатная должность в этой таблице — справочная колонка, а не основание.** Она стоит в конце намеренно. Если у человека Compa-ratio 2.09 при роли «Администратор проекта», а в графе должности значится «Руководитель проекта» — это подсказка, откуда взялся оклад, но цифра посчиталась без её участия.

# Вкладка 6 — Качество данных

**Вопрос:** можно ли верить всему предыдущему. Открывать первой при каждом обновлении.

### KPI

`Доля подтверждённых ЗП` · Строк без ЗП · Людей с неподтверждённой ЗП · `Продуктов с 1 человеком` · Должностей вне классификатора

### C6.1 — Заполненность

- **Тип:** Линейчатая. **Y:** название проверки · **X:** число проблемных строк
- **Цвет:** статусный — 0 зелёный, > 0 красный, с подписями
- Источник — лист «Проверки» из XLSX; можно просто продублировать его таблицей

### C6.2 — Проблемные строки

- **Тип:** Таблица. **Фильтр:** `ЗП подтверждена` = 0 ИЛИ `Уровень роли №` = −1
- **Колонки:** `Строка` · `Сотрудник` · `Проект` · `Штатная должность` · `ЗП` · `Комментарий`
- **Зачем.** Это не отчёт, а список задач. Прошли по нему, поправили в источнике, перегенерировали датасет — вкладка пустая.

### C6.3 — Сверка итогов

Небольшая таблица, сравнивающая метрики, посчитанные двумя независимыми способами:

| Метрика | Способ 1 | Способ 2 |
|---|---|---|
| Численность | `SUM([Первичное назначение])` | `COUNTD([Сотрудник])` |
| ФОТ | `SUM([ФОТ аллоцированный])` | `SUM(IF [Первичное назначение]=1 THEN [ЗП] ELSE 0 END)` |
| Проектов | `COUNTD([Проект])` | 12 (константа) |

Расхождение означает, что поехали доли или появились дубли. Самая дешёвая страховка от тихой ошибки в цифрах, которую иначе замечают через полгода.

# Вкладка 7 — Динамика

**Вопрос:** что изменилось с прошлого раза. Единственная вкладка, отвечающая не на «как сейчас».

**Источник — отдельный датасет** на файле `datalens_dataset_history.csv`: там все накопленные срезы, а не только последний. Гранулярность та же, что у основной таблицы, поэтому любое поле переносится без переделки — добавляется только измерение `Дата среза`.

Вкладка начинает работать со **второго** среза. На первом запуске смотреть нечего, но копить надо с него.

### KPI

```
ФОТ, мес             = SUM([ФОТ аллоцированный])
Людей                = COUNTD([Сотрудник])
Прирост ФОТ, %       = ([ФОТ, мес] - LAG([ФОТ, мес], 1)) / LAG([ФОТ, мес], 1)
Прирост людей, %     = ([Людей] - LAG([Людей], 1)) / LAG([Людей], 1)
Рост цены команды    = [Прирост ФОТ, %] - [Прирост людей, %]
```

⚠️ `LAG` — оконная функция, ей нужна ось сортировки: в настройках поля укажите упорядочивание по `Дата среза`.

### C7.1 — ФОТ и численность по срезам

- **Тип:** Комбинированная. **X:** `Дата среза` · **Y1:** ФОТ линией · **Y2:** численность столбцами
- **Зачем.** Здесь видно то, ради чего история и нужна: **растёт ли ФОТ вместе с командой или отдельно от неё.**
- **Как читать.** ФОТ +8% и команда +8% — вы наняли людей. ФОТ +8% при неизменной команде — вы пересмотрели зарплаты. На статичном срезе эти два случая неразличимы, а решения по ним противоположные. Именно это и показывает `Рост цены команды`: около нуля — рост за счёт найма, заметно больше нуля — за счёт пересмотров.
- **Нюанс.** Две оси Y здесь оправданы (это единственное исключение из общего правила): величины разной природы, и смысл чарта именно в их расхождении.

### C7.2 — Что изменилось

- **Тип:** Таблица. **Источник:** `datalens_dataset_changes.csv`
- **Колонки:** `Событие` · `Сотрудник` · `Проект` · `Было` · `Стало` · `Δ руб` · `Δ %`
- **Селектор:** `Событие` — по умолчанию снять `Вакансия висит`, иначе она забьёт таблицу
- **Зачем.** Это то, что реально смотрят раз в месяц за пять минут. Всё остальное отвечает на «как сейчас», эта таблица — на «что произошло».

### C7.3 — Движение людей

- **Тип:** Столбчатая с накоплением. **X:** `Дата среза` · **Y:** число событий · **Цвет:** `Пришёл` / `Ушёл`
- **Разрез:** селектор по `Блок` — текучесть по направлениям становится видна сама

### C7.4 — Зависшие вакансии

- **Тип:** Линейчатая. **Y:** продукт и роль · **X:** сколько срезов подряд открыта
- **Зачем.** Вакансия, висящая четвёртый месяц, — это либо ненужная позиция, либо не та вилка. В срезе она выглядит одинаково и на первый день, и на двухсотый.

> **Что история создаёт сама.** Через год накопления из неё выводится дата последнего пересмотра зарплаты — это последний срез, в котором `ЗП` человека изменилась. Отдельного столбца для этого вести не нужно, а поле `Просрочен пересмотр` из группы 8 становится считаемым. Часто именно там прячется риск ухода, а не в Compa-ratio.

## Часть 4. Права доступа

Дашборд с зарплатами всей организации — самый чувствительный документ, который у вас будет. **Настраивать до того, как дать кому-либо ссылку.**

| Кто | Что видит |
|---|---|
| Вы, HR, финансы | Всё |
| Ответственный за блок | Свой блок с зарплатами |
| Руководитель | Своих подчинённых |
| Остальные | Обезличенная копия либо ничего |

**RLS** настраивается в датасете, в свойствах поля `Блок`:

```
'user1@company.ru': Радужан А.А.
'user2@company.ru': Зазыкин В.Г., Ульянов А.Ю.
'hr@company.ru': *
```

Проверять обязательно через режим **«Просмотр от имени пользователя»**: на словах RLS всегда настроена правильно, а на практике почти всегда с первого раза протекает.

**Обезличенная копия** — отдельный дашборд на том же датасете, но без полей `ЗП`, `Compa-ratio`, `Отклонение руб`, `База сравнения`, `Доплата до порога`. Остаются состав команд, загрузка, уровни ролей, вакансии, bus factor. Такой дашборд полезен всем и не создаёт рисков.

**Расчёты**

## Часть 6. Как этим пользоваться дальше

Дашборд сам по себе ничего не меняет. Работает регулярный цикл:

**Ежемесячно, 15 минут.** Перегенерировать датасет с новым `--snapshot`, открыть вкладку 6 (данные в порядке?), затем вкладку 3 (кто перегружен). Поправить назначения.

**Ежеквартально, 1–2 часа.** Вкладка 2, но не весь список подряд, а в три захода:

1. **Сначала «Недоплата»** (25 человек, Compa < 0.80) — самые острые случаи, отсортированные по рублям. Особое внимание тем, где сошлись Compa-ratio и IQR.
2. **Потом «Ниже роли»** (14 человек) — кандидаты на пересмотр в следующем цикле.
3. **В конце «Переплата»** (11 человек) — здесь не решение, а вопрос: чем обоснован оклад выше остальных, кто делает ту же работу. Часто ответ окажется в графе штатной должности, и тогда обсуждать надо не зарплату, а то, какую работу человек на самом деле должен делать.

По каждому решению — **записывать причину**. Через два-три квартала накопленные причины станут тем, чего сейчас не хватает: объяснением, почему за одну и ту же роль платят по-разному. Тогда Compa-ratio из списка на разбор превратится в вердикт.

**Раз в полгода.** Вкладки 4 и 0. Оргструктура меняется медленно.

**Перед бюджетированием.** What-if калькулятор и плитка «стоимость вакансий»: три сценария индексации плюс прогноз прироста ФОТ при закрытии набора. Разговор с финансами идёт по числам, а не по ощущениям.
